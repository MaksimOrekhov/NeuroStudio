# NS-005A — ComfyUI disconnect investigation

Дата: 2026-11-09. Только чтение логов и событий, новых генераций и перезапусков не было.

## Вывод

**Причина отключения подтверждена:** процесс ComfyUI аварийно завершился (access violation в `c10.dll` из PyTorch) во время VAE-декодирования первого кадра второй коллекции. Это не NeuroStudio, не конфликт портов и не запуск двух экземпляров.
**Первопричина самого краша не установлена.** Есть сильная гипотеза (исчерпание виртуальной памяти Windows), но она не доказана.

## Точная ошибка

- NeuroStudio: `ComfyUI not reachable at http://127.0.0.1:8188: fetch failed` (`ComfyUnavailableError` при опросе `/history`).
- ComfyUI (`logs/comfyui.log`, `Windows fatal exception: access violation`), стек: `comfy/sd.py:1375 decode` ← `nodes.py:343 VAEDecode` ← `execution.py`.
- Windows (Application Error 1000 / WER APPCRASH, 19:37:11): `python.exe` (`standalone-env`), модуль `torch\lib\c10.dll`, код `0xc0000005`, смещение `0x8ddd4`, PID `0x39AC` = 14764.

## Что показывают логи и события

- **Это повторяющийся дефект установки, не связанный с NeuroStudio.** Та же подпись (`c10.dll`, `0xc0000005`, стек в `decode`, ~20 ГБ виртуальной памяти, событие 2004) зафиксирована ещё 3 раза: 7 ноября в 20:39, 20:41 и 20:49 — до появления NeuroStudio и сразу после обновления ComfyUI до 0.44.2 (20:20). Файлы дампов есть для всех четырёх случаев.
- **Нехватка виртуальной памяти вероятна:** pagefile задан вручную (8 ГБ на `D:`, автоуправление выключено), лимит commit около 39 ГБ при 31 ГБ RAM; во всех четырёх событиях `python.exe` занимал около 20 ГБ. Сам факт нехватки на момент краша (commit у лимита) не измерялся, дамп не разбирался.
- OOM по CUDA в логах нет, ошибок драйвера/TDR в системном журнале нет.
- Окончательное состояние задания `615d2134…`: ComfyUI упал при декодировании, файла `NeuroStudio/monsoon-courtyard-bellmaker/scene-01…` в его `output` нет; история ComfyUI живёт в памяти процесса и после краша потеряна, подтвердить статус через `/history` нельзя.

## Процессы и порты

- В 19:10 Desktop запустился, пока мой отдельный экземпляр (из NS-004) занимал 8188; Desktop по своему `app.log` оставил его («held by a ComfyUI … left running») и не стартовал второй. После моей остановки того экземпляра Desktop поднял свой в 19:15:33.
- В момент сбоя порт держал один процесс — ComfyUI Desktop (PID 14764). Одновременной работы двух экземпляров не было, переключения Desktop на другой порт нет. Перезапуска бэкенда Desktop до краша не было; после краша `python.exe` не поднят, порт свободен.
- Замечание: мой отдельный запуск `main.py` рядом с Desktop создавал путаницу в диагностике и больше не нужен.

## Поведение NeuroStudio

Проверено по манифестам и коду:

- `prompt_id` сохранён в `collection.json` (`615d2134-…`) — не потерян.
- Повторной отправки нет: в логе один `scene-01: submitting` для коллекции 2; `submit` вызывается один раз.
- Коллекция 1 цела (4 PNG, статус `done`), `batch-plan.json` со статусом `failed` и текстом ошибки.
- Бесконечного ожидания нет: сетевая ошибка бросается сразу, запрос ограничен 15 с.
- В интерфейсе: «Run stopped at collection 2 / 2: … Completed collections are saved below», карточка коллекции 2 с ошибкой.

**Найден один дефект и исправлен (уже в PR #4):** кадр, принятый ComfyUI, но потерянный из-за пропавшего ComfyUI, записывался как `failed`, хотя реальное состояние неизвестно. Теперь такой кадр получает неопределённый статус (`timeout`, в UI «Unknown state» с `prompt_id`), как и при таймауте. Добавлен один тест (`tests/autopilot.test.ts`). Ранее записанный манифест этого запуска сохранил старый статус `failed`; данные не переписывались.

## Нужны ли изменения кода

Больше нет: автоматическое восстановление и менеджер процессов не добавлялись (по условию).

## Как избежать повторения (рекомендации, ничего не менялось)

1. Запускать ровно один ComfyUI (Desktop) и только его использовать с NeuroStudio; не запускать параллельно отдельный `main.py`.
2. Проверить файл подкачки: поставить автоматическое управление или увеличить pagefile (сейчас фиксированные 8 ГБ).
3. Если краши продолжатся, попробовать запуск ComfyUI с `--disable-dynamic-vram` (флаг есть в `comfy/cli_args.py` версии 0.44.2) и сравнить; при повторении передать дамп `python.exe.14764.dmp` и версию в Comfy-Org как баг. Это решения пользователя.
4. После краша перезапустить ComfyUI и начать новую партию; незавершённые `prompt_id` из манифеста можно только проверить вручную, в истории перезапущенного ComfyUI их не будет.

## Можно ли сливать PR #4

Да. NeuroStudio отработал сбой корректно (сохранил готовое, не повторил задания, показал место остановки), краш в ComfyUI вызван средой и воспроизводился до NeuroStudio. Оговорка: сквозной прогон двух коллекций не завершён и не подтверждён на GPU; его можно повторить после мер выше.
